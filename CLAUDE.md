# hydra – instructions for agents

hydra is a fantasy survival RPG: you rise either as a humanoid hero or as a monster that
evolves (slime, wolf, saurian lines). It is planned in phases: **arena** (Phase 1/1b) →
fixed maps on dedicated servers (Phase 2) → MMO (Phase 3). This repository is built mostly
by AI agents; a human decides design questions and does the playtests.

## Read first

1. `README.md` – what is where.
2. `docs/roadmap.md` – the current phase and milestone. **Build only what the current
   milestone asks for.**
3. `docs/design/phase-1.md` – the rules to implement.
4. `GLOSSARY.md` – the one English name for every game term. Use it in code, data and docs.
5. `docs/tech/tech-test-findings.md` – what worked and what didn't in the Unreal tech test.

The full design notes are in German and live outside this repo. If something is missing or
unclear in `docs/design/`, make a reasonable assumption, write it in `docs/dev-log.md` and
carry on; the human moves settled answers into the design doc.

## Engine and setup

- **Unreal Engine 5.8** (launcher build), Windows, Visual Studio toolchain. The engine path
  is local; scripts read it from the environment variable `UE_ROOT`
  (e.g. `D:\dev\Epic Games\UE_5.8`).
- The launcher build cannot build a dedicated **server target**. Phase 1 runs in host mode
  (listen server), so that is fine; a source-built engine comes in Phase 1b.

## Principles

- **Logic in C++, not in Blueprints.** Blueprints are binary and hard for agents to read. At
  most thin Blueprint subclasses for asset assignment. Animation logic in a C++
  `UAnimInstance` (pattern from the tech test) until a decision says otherwise.
- **Assets by script.** Maps, FBX imports and materials are created headlessly with Python
  commandlets in `Scripts/` (`UnrealEditor-Cmd.exe … -run=pythonscript -script=…`).
  Models, rigs and animations come from Blender scripts (`docs/tech/blender-pipeline.md`).
  Any step a human has to do by hand in an editor is an **intervention** → `docs/dev-log.md`.
- **Never hard-code gameplay values.** Every gameplay number comes from `data/values.json`,
  loaded at runtime and reloadable without recompiling (console `Hydra.ReloadValues`). Level
  layout and weapon geometry may live in code or assets.
- **Server-authoritative.** Every gameplay decision (hits, damage, stamina, mana, block,
  level-ups, evolution) is made on the server, also in host mode. Clients predict only what
  the engine predicts well (movement, ability activation).
- **Positional combat, no timing windows.** There is no parry and no perfect dodge. Hits
  depend on position, facing and hit areas; dodge is pure movement without invulnerability.
  Hit and block checks use **lag compensation** (rewind to what the attacker saw).
- **GAS** (Gameplay Ability System) for attributes, abilities and effects, behind a small
  own helper layer that hides the C++ boilerplate (effects as native classes, values via
  SetByCaller, see the findings doc).
- **Data-driven.** Forms, skills, elements, weapons and numbers are data files with stable
  IDs – the basis for balancing and later mods.

## Data

- `data/values.json` is the single source of gameplay numbers. The dev checkout reads it
  directly; the build copies it to `Config/Hydra/values.json` for packaged builds.
- Adding or changing a value: edit `data/values.json`, bump `version`, add a line to
  `data/CHANGELOG.md` (what and why), map it in the C++ struct. An automation test checks
  that every key is mapped.
- Starting values are guesses to be tuned in playtests; mark new guesses as such in the
  changelog.

## How to work

- Work through `docs/roadmap.md` in order; tick items when they are done and verified.
- **Verify from the command line** before every commit: build, automation tests
  (`Scripts/run_tests.sh`), and for gameplay a scripted live run (host plus client window,
  automated input, screenshots). Never claim something works without having run it.
- Small commits with a clear message; keep `main` building.
- **Unclear:** don't wait – assume, log it, carry on. **Blocked:** after two serious
  attempts, document it in the dev log and move to the next item.
- Prefer text files and the command line. Avoid editor-only workflows.
- Don't add features beyond the current milestone; note ideas in the dev log instead.

## Dev log (`docs/dev-log.md`)

Keep it current while working: session start and end, what was done per roadmap item,
**interventions** (every manual editor step by a human), assumptions, problems and
workarounds.

| `Art/` | Blender sources (`.blend`, Git LFS) and Blender Python scripts |
